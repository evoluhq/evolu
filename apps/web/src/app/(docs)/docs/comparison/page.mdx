# Comparison

This page gives an overview of local-first, offline-first, and sync tools and how they work.

In 2019, Ink & Switch published [Local-first software](https://www.inkandswitch.com/essay/local-first/), an essay about software in which the data on the user's devices is the primary copy. Servers still exist, but they hold secondary copies, and the software keeps working when they go away.

Many people take local-first to mean offline-first: an app that keeps working without a network and syncs later. Working offline is one of the essay's seven ideals, not its definition. An app whose server decides what the data is, by ordering writes or making devices undo them, is offline-first, however well it works offline.

Two things follow from the essay, and local-first software can't do without either:

- **No dependence on one server.** When servers hold only copies, any of them can be replaced. In his [2024 Local-First Conf keynote](https://www.youtube.com/watch?v=NMq0vncHJvU&t=1073), Martin Kleppmann, one of the essay's authors, described the local-first endgame as generic syncing services that speak an open protocol, so users can switch between providers. His [2026 QCon keynote](https://martin.kleppmann.com/2026/03/17/qcon-keynote-geopolitical-risk.html) names "easy provider switching" as what local-first aims for. Evolu Relay works this way for Evolu apps.
- **The server knows nothing about the data.** A provider that can read the data can watch its users, hand the data over, or use it against them, so the data isn't really theirs and they aren't safe. Local-first software therefore encrypts data end to end, always. Encryption that can be left off leaves data readable: Telegram encrypts end to end only secret chats, which users start one by one, so its default chats and all its groups are readable by Telegram. Signal encrypts every message, with nothing to turn on. Some metadata stays visible, because no usable system works without it: even Signal's servers see IP addresses and network activity. [What relays see](/docs/privacy#what-relays-see) lists what Evolu's relays see.

Unfortunately, marketing also uses "local-first" for products that aren't local-first. Calling them "local-first-ish" doesn't help either; that is on the edge of disinformation.

## Criteria

1. **Works offline.** Reads and writes work without a network, and the device keeps them across restarts.
2. **The device's copy is primary.** Each device merges changes itself. No server decides which write wins or makes a device undo a write.
3. **Full history.** Every change is kept, including changes a newer one overwrote, so no write is lost and a device merges safely however long it was offline.
4. **No single server.** The app can sync through any server, its own included, and switch servers without losing data.
5. **End-to-end encryption, always on.** Servers store data they can't read, and no setting turns the encryption off.
6. **Post-quantum cryptography.** Neither the encryption nor the signatures that grant access or vouch for changes rely on cryptography a quantum computer can break. Encrypted data can be recorded now and decrypted once quantum computers exist, and a broken signature key could backdate a grant or a write that other devices accept as a late change.
7. **Keys, not accounts.** The user's identity is a key on the device. A sync provider may bill through an account, but the account doesn't decide who the user is or who can access the data.
8. **Open source.** The client and the server are open source, so the software can outlive its vendor.

Local-first software meets all eight, and a feature that is optional or experimental counts as missing. A product that calls itself local-first but doesn't meet all eight is not local-first yet when it's open source, works offline, and no server decides or reads its data by design, though one may partly or by default, for example when end-to-end encryption is optional or unfinished. So is a product that meets all eight before it's finished: in alpha, experimental, or before version 1.0, which [semantic versioning](https://semver.org/#spec-item-4) defines as initial development. A product that calls itself local-first while it doesn't work offline, a server decides or reads its data by design, or it isn't open source is only marketed as local-first. Any other product that works offline is offline-first, and one that doesn't is a sync engine.

### Evolu

Evolu stores data in SQLite on each device and syncs changes, encrypted end to end, through relays the app chooses, including relays it runs itself. Each device merges the changes it receives: for each column, the latest change wins, so devices with the same changes have the same data, as [Sync](/docs/sync) explains. Every synced change stays in the history, which apps can query, as [Time travel](/docs/time-travel) shows. A relay serves any Evolu app and stores changes it can't read. Data belongs to owners, each identified by a secret on the device, not by an account on a server.

Beyond local-first, Evolu offers:

- **SQL.** Apps query SQLite with typed queries.
- **Several relays at once**, self-hosted and cloud ones combined, as [Relay](/docs/relay) describes.
- **A binary protocol** built for size and speed. It finds the changes each side is missing with range-based set reconciliation, so relays keep no state per client. See [Protocol](/docs/api-reference/common/local-first/Protocol) and [Scaling local-first software](/blog/scaling-local-first-software).
- **Local auth.** A passkey, the iOS Keychain, or the Android Keystore protects the owners' secrets on the device, with no server involved. See [Local auth](/docs/local-auth).
- **An encrypted database on the device.** See [Encryption on the device](/docs/privacy#encryption-on-the-device).

## Marketed as local-first

These products call themselves local-first, but they don't work offline, a server decides or reads their data by design, or they aren't open source. Evolu doesn't consider them local-first: the term promises users data that is theirs and safe, and these products don't deliver it and can't without a rewrite or, for closed-source products, a new license. Calling them local-first is marketing, even when the product itself is a good offline-first tool.

## Offline-first

These products work offline and don't call themselves local-first. Offline-first is a fine choice, and we have nothing against it. A server that orders writes, enforces constraints, and checks permissions, as many of them have, makes many apps simpler, and their users can still work offline. It's a trade-off: offline-first isn't local-first, which strengthens users' sovereignty and gives them real ownership of their data.

## Sync engines

Every local-first tool is a sync engine, but not every sync engine is local-first, or even offline-first. Many only mirror data from a server and can't write without a connection.

The [localfirst.fm landscape](https://www.localfirst.fm/landscape) takes local-first so broadly that sync engines fit in it, even ones without offline writes. In [its data](https://github.com/localfirstfm/local-first-landscape), which the technology creators maintain themselves, 10 of the 22 entries state that their authority is centralized.
