# Privacy

Privacy is fundamental to local-first software, and Evolu takes it seriously. Unlike traditional client-server applications where data lives on someone else's servers, Evolu ensures that data remains under the user's complete control while providing the synchronization and backup benefits needed.

## End-to-end encryption by default

All data Evolu syncs is encrypted end-to-end. This means:

- Data is always encrypted when it leaves the device
- The Evolu Relay receives only encrypted data
- Only devices with the correct encryption keys can decrypt the data
- Even if someone intercepts the data in transit or gains access to the relay, they see only meaningless encrypted bytes

## Encryption on the device

- **Web and Electron** (React, Svelte, Vue, and vanilla JS with `@evolu/web`): encrypted. `@evolu/sqlite-wasm` encrypts every page of the database and its rollback journal in SQLCipher 4's format as the `sqlcipher` scheme of SQLite3 Multiple Ciphers writes it, with AES-256-CBC and HMAC-SHA512.
- **React Native and Expo**: encrypted with SQLCipher only when the app enables it in the `expo-sqlite` config plugin with `"useSQLCipher": true`, as the [react-expo example](https://github.com/evoluhq/evolu/tree/main/examples/react-expo) does in its `app.json`. Without it, `expo-sqlite` builds plain SQLite, which ignores the key, so the database is stored unencrypted. Evolu doesn't check for it. In a React Native app that doesn't run Expo's prebuild, set what the plugin would write yourself: `expo.sqlite.useSQLCipher=true` in `android/gradle.properties` and `"expo.sqlite.useSQLCipher": "true"` in `ios/Podfile.properties.json`.

With the `memoryOnly` option, the database is kept in memory and nothing is stored on the device.

## API design prevents data leaks

Evolu's API is designed to prevent developers from accidentally leaking sensitive data:

- **No public data options**: There is no API to mark data as "public" or "unencrypted"
- **Can't be disabled**: No option turns off end-to-end encryption. Only the database on the device needs setup, in React Native and Expo, as [described above](#encryption-on-the-device)
- **Explicit plaintext export**: `exportDatabase` returns the whole local database as a plain, unencrypted SQLite file, so users can open their data in any SQLite tool. Apps should treat that file as sensitive

## Traffic analysis protection

To prevent traffic analysis attacks, Evolu uses message padding (PADMÉ)—a [technique](https://lbarman.ch/blog/padme/) that pads binary messages to obscure their actual size. Combined with end-to-end encryption, message sizes don't reveal the data. Timestamps and NodeIds still reveal activity, as described below.

## Relay blindness by design

The Evolu Relay is completely blind to user data. What the relay sees:

- **OwnerId**: A unique identifier for the data owner (but not who that owner is)
- **Timestamps**: When changes occurred (for synchronization ordering)
- **NodeId**: Every timestamp includes a random ID of the database that wrote the change. It's the same for every owner the database writes changes for, so a relay can link those owners, even across IP addresses
- **Encrypted binary blobs**: The actual data, completely encrypted and padded to obscure size
- **Write key**: A token that authorizes writes for an owner. By default, it's the same on every relay the owner uses
- **IP addresses**: Network addresses of connecting clients (standard for any network service unless using Tor or similar privacy networks)

The relay functions purely as a message buffer for synchronization and backup—it stores and forwards encrypted messages without any ability to decrypt them.

The relay stores what it sees in a plain SQLite file. The changes are already encrypted end-to-end, and the relay needs the rest to sync.

## Timestamp metadata

Relays and collaborators can see timestamps (user activity). This does not increase risk compared to any real‑time messaging system where traffic timing is observable.

### Why timestamps are visible

Real‑time communication inherently reveals that “something happened” (bytes were transferred). Even if we hid explicit timestamps, an observer could record packet timing. Relying on participants not to store this information is unsafe, so explicitly exposing timestamp metadata doesn't add additional risk.

### Mitigating activity leakage

If maximum privacy is required (e.g., hiding interaction cadence), an application can implement a local write queue:

1. Write changes immediately to a local‑only table
2. Periodically and randomly flush messages to sync tables

The trade-off is that collaboration is no longer real-time.

## Post-quantum resistance

In a "harvest now, decrypt later" attack, an adversary collects encrypted data today and waits for a quantum computer to decrypt it. Encrypted data can be collected by a relay operator, by anyone who breaches a relay, or by anyone recording network traffic. Evolu is designed so that such data stays encrypted.

### Why symmetric encryption

A large quantum computer running Shor's algorithm could break public-key cryptography such as RSA and elliptic curves. Evolu sync doesn't rely on it. Changes are encrypted with XChaCha20-Poly1305 under a 256-bit symmetric key, and the Evolu Relay never sees or stores public keys.

The best known quantum attack on symmetric cryptography is Grover's algorithm, which searches N possibilities in about √N steps. That halves the bits of security, so a 256-bit key keeps about 128 bits.

### Where the keys come from

Each owner's keys are derived from its owner secret with SLIP-21 (HMAC-SHA512):

- **OwnerId**: the public identifier that relays see
- **Encryption key**: the 256-bit key that encrypts the owner's changes
- **Write key**: a token relays check before accepting changes; it controls who can write, not who can read

### How much entropy is enough

Since every key is derived from the owner secret, an owner's keys are only as strong as that secret: an attacker can test guesses offline against the public OwnerId.

`createOwnerSecret` generates 32 random bytes, shown to users as a 24-word mnemonic. Against a quantum computer, that leaves about 128 bits of security, which matches NIST's highest post-quantum category (at least as hard as breaking AES-256). NIST still accepts its lowest category (AES-128) because Grover's algorithm parallelizes poorly, but Evolu targets the highest because local-first data may need to stay private for decades.

| Owner secret | Mnemonic | Classical security | Quantum security |
| ------------ | -------- | ------------------ | ---------------- |
| 32 bytes     | 24 words | 256 bits           | about 128 bits   |
| 16 bytes     | 12 words | 128 bits           | about 64 bits    |

Evolu also accepts owner secrets of 16 to 28 bytes (12 to 21 words), for example for owners created by other apps. A 16-byte secret still gives 128 bits of security against classical computers, which is far beyond any classical attack, but leaves less margin against a future quantum computer. That can be the right trade-off: a 12-word or 20-word backup is easier for users to write down and check, and not every app's data needs to stay private for decades. A mobile wallet meant for small amounts is an example. Its Bitcoin keys rely on elliptic curves that a quantum computer could break anyway, so a longer backup phrase would cost usability without removing that risk.

Length alone is not entropy. A secret derived from a smaller root is no stronger than the root, because derivation can't add randomness. For example, a 32-byte owner secret derived from a 20-word SLIP-39 share, which holds 16 bytes, has only 128 bits of entropy.

When data must stay private long term:

- Create owner secrets with `createOwnerSecret`, or restore them from the 24-word mnemonic Evolu shows.
- If you derive owners from your own root secret, give that root at least 256 bits of entropy, such as a 24-word BIP-39 mnemonic or a 33-word SLIP-39 share.
