Yesterday, Signal published
[Signal is Serious About Protecting Your Privacy](https://signal.org/blog/protecting-your-privacy/),
explaining why it is blocking screenshots on iOS 27 and when AI assistants try
to read the screen on Android—following its
[Windows 11 screen-security change](https://signal.org/blog/signal-doesnt-recall/)
for Microsoft Recall last year. The core problem applies to every privacy-sensitive
app, including apps built with Evolu: operating systems now ship AI agents that
read what appears on screen, above the layer where encryption works.

Signal's post also points out that blocking screenshots doesn't stop an agent
from reading files already on the device. That splits the problem into two
halves: data at rest on disk, and data once the app unlocks and renders it.

## What Evolu closes on disk

Many web and local-first apps leave user data in plaintext in `localStorage`,
IndexedDB, OPFS, or plain SQLite files. On a desktop or browser profile, any
program that can read the user's files can read that storage directly, without
ever touching the screen.

Evolu encrypts every database an app stores on the device page by page with
AES-256 and keeps SQLite's temporary files in memory. With a `DeviceSecret`—kept
in the iOS Keychain, encrypted with an Android Keystore key, or unlocked by a
passkey on the web via
[`createPasskeyAuth`](/docs/api-reference/web/functions/createPasskeyAuth)—a
program that can only read the app's files gets ciphertext, even in a browser.
(With `InstantStart`, the device database's key is public, so stored files remain
readable; [Local auth](/docs/local-auth) explains the trade-off.)

That doesn't set Evolu apart from Signal: Signal encrypts its local SQLite
database with SQLCipher on every platform too. It sets encrypted local-first
storage apart from plain browser and SQLite storage.

## Where encryption stops

Once an app unlocks its database and puts data on screen, encryption can no
longer protect it. That boundary is the same for every app:

- **The screen**: Screenshots, screen recording, app-switcher snapshots, and OS
  AI features such as Windows Recall, Android Gemini Screen Context, and Siri AI
  read rendered output after decryption.
- **Accessibility**: Operating-system assist frameworks and third-party agents
  that users grant accessibility permissions can inspect the app's view tree or
  DOM.
- **Notifications and the clipboard**: Anything an app puts into a notification
  or copies to the clipboard leaves the app's boundary in plaintext, where the
  OS, notification listeners, and clipboard managers can read it.
- **Unlocked memory and the browser**: While a tab is open and unlocked,
  decrypted data and keys live in JavaScript and WebAssembly memory, accessible
  to browser extensions and any built-in browser AI feature allowed to read the
  active tab.

For an Evolu app, the most sensitive screen is usually the recovery view showing
an owner's mnemonic: a single capture of those words gives permanent access to
the owner's synced history on relays. Keep it hidden until the user asks to see
it, and avoid putting sensitive content into notifications.

## Why Evolu doesn't block capture for you

Evolu is a storage, encryption, and sync library. It owns no window, view
hierarchy, or notification layer, so screen protection belongs in the app.

Even if Evolu could toggle platform flags, one default wouldn't fit every app.
Blocking screenshots prevents legitimate screenshots and screen sharing, and—as
Signal noted when enabling it on Windows 11—can break some accessibility tools.
A todo app and a private journal make different trade-offs, and many apps only
want capture protection on a single sensitive screen rather than across the
entire window. On iOS, blocking screenshots also relies on undocumented UIKit
internals that can break with OS updates or view-hierarchy changes, which
doesn't belong inside a database library.

Evolu's job is to keep the boundary clear: encrypt synced changes end to end,
encrypt databases on disk, and document honestly where that protection ends. See
[What encryption doesn't protect](/docs/privacy#what-encryption-doesnt-protect)
for the short reference in the docs.
